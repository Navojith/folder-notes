- **I do not know which of the two, or whether the tracker is involved at all.** Correlation only. It is the first shell crash of

### F2. Against a genuinely frozen Explorer process, `CoCancelCall` returns instantly but does not release the call (closes O-25 negatively)

Setup (safe by construction): a **separate** `explorer.exe` that the lab started with `/separate`, verified not to be the shell and
to host no earlier window, frozen with `NtSuspendProcess` for about 12 s, a detached helper to resume it, the shell never touched.
Observed (`artifacts/t325/hung-explorer.md`, first sweep):

| Time after freeze | Observation |
|---|---|
| 0.5 s | 1 cancel issued by the watchdog; `CoCancelCall` took **0.01 ms**; call still blocked |
| 1.5 s | worker abandoned (as designed), replacement started |
| 2.5 s | the replacement worker also blocked (it enumerates, and touches the frozen process's tabs); second abandon |
| 3 s | third abandon, **circuit breaker tripped: tracker `Disabled`**, `Inactive` published |
| frozen window kept foreground | no recovery; after resume still `Disabled` (needs the explicit Retry) |
| healthy lab window foreground meanwhile | **not followed** (tracker disabled): the test failed on this |

So `CoCancelCall` is *accepted* quickly (the 50 ms contingency trigger of O-25 is **not** hit: max 0.01 ms) but it **did not unblock
the call** on a real Explorer proxy (P2 had shown it working on the scratch server). With cancellation ineffective, only
abandonment remains: each replacement worker re-touches the frozen process and wedges too, so one frozen Explorer window process
disables tracking of all windows within about 3 s, until the user retries. The UI was never blocked (heartbeat max 0.69 ms), `Stop`
returned in 2 ms, and the zombie's late evaluation (12 s) published nothing, so ADR-025's *bounded harm* holds; its *availability*
goal does not. This needs a design decision (for example: remember which tab/process wedged and skip it, or time-box per tab),
so I changed nothing. The 50 ms contingency (abandon deadline on a pool timer) would not help: the cancel is not slow, it is ineffective.

## Measurements and methodology

- **Latency** = from just before the action (`Navigate2`, a key chord, `SetForegroundWindow`) to the moment the
  `ActiveFolderChanged` handler runs on the (stand-in) UI thread: it includes Explorer's own work, the WinEvent, the evaluation and
  the hand-off. Percentiles by nearest rank. The 5 ms heartbeat bounds the hand-off at under 0.3 ms.
- **Oracle**: `Shell.Application` (`Document.Folder.Self.Path`) and the frame title, independent of the tracker's interop.
- **Idle CPU**: whole test process, first with `GetProcessTimes` (15.6 ms tick; unreliable), then `QueryProcessCycleTime`
  calibrated against a spin; the final calibration has a defect (the first read includes the spin), so the baseline row is invalid.
- **Foreground theft**: the desktop was in use (Chrome repeatedly took the foreground). A failing attempt with a foreign
  foreground change is repeated (≤ 3); no reported number came from a repeated attempt.
- Not measured: `CoCancelCall` latency against a *responsive but slow* Explorer; Windows 10; mixed DPI; the shell-process window
  case (every lab window lived in its own process).

## Cleanup items (asked for)

- **Control characters:** the affected file was `ExplorerLogicSourceGuardTests.cs`; the characters were **backspace (0x08)**, not BEL,
  from a `\b` regex escape slip (5 places). They had made 3 guard regexes unmatchable, so those guards (no thread/timer/COM in the
  engine; the watchdog touches no hook or COM object; COM types only in `Com/`) **were passing vacuously since T3.2.3/T3.2.4**.
  Fixed; a mutant (a `Marshal` call in `TrackerEngine`) now fails two guards. Fixing them exposed one false positive (a log string
  naming `IShellWindows`), so the guard now ignores string literals. A scan of tracked files finds no other control characters.
- **Latest-wins:** intentional; written into 04 § D.8 together with the consumer contract. In the rapid runs published = delivered
  (no merging happened), so the merging is untested on real Explorer; the deterministic tests cover it.
- **Deterministic versus timing:** every tracker test class is tagged `Kind=Deterministic` or `Kind=Timing` (and the two concurrent
  stress tests individually), `Kind=RealExplorer` for the real suite; rule in 06. Full App suite: 619 tests, 0 failed, 14 skipped (the real suite).

## Outstanding specification issues

- **S1** (REQ-031 evaluation cost): "< 10 ms" is not met at p95 on a busy Explorer (the read waits for Explorer's UI thread). Either
  define the bound on the median plus an end-to-end 150 ms (which the data supports) or on the tracker's own CPU; needs your call.
- **S2** (NFR-06 idle): 0.096 % best case against < 0.1 %, mostly the 2 s poll; consider a longer slow-poll interval or a cheaper
  poll. Needs a clean re-measure on a quiet VM.
- **S3** (ADR-025/D4): F2 above.
- **S4** (04 L12/L8 etc.): plain `explorer.exe <path>` windows are hosted outside the shell process on this build, so "hook scope =
  the shell's process" is rarely true in practice; the scoping logic is unaffected.
- **S5**: Explorer accepts at most about 46 tabs via Ctrl+T on this build; the 50-tab criterion in 06 should say 40.
