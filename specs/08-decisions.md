# 08 — Architecture Decision Records

Status values: **proposed** → **accepted** / **rejected** / **superseded by ADR-xxx**.

---

## ADR-001: WinUI 3 + C# for the app — *accepted (amended 2026-10-31)*

> **Amendment:** .NET 8 LTS goes out of support in November 2026. Target **.NET 10 (LTS)** with
> **Windows App SDK 2.x** (2.5.1 verified in spike S2). The spikes ran on .NET 9 because only the
> .NET 9 SDK is installed. Installing the .NET 10 SDK is a prerequisite for T1.1.


**Context:** The UI needs to look native to Windows 11 (Mica, Fluent controls, dark mode,
accessibility) and work closely with Win32/COM (Explorer automation, hotkeys, window ownership).
**Options:** WinUI 3; WPF + WPF-UI; Tauri/Electron; Avalonia.
**Decision:** WinUI 3 (Windows App SDK) with C#.
**Consequences:** Best native fidelity and direct access to Win32 interop through CsWin32. Tool-window
behaviour needs some Win32 work (spike S2). Windows only, which is a stated non-goal anyway.
Electron and Tauri were rejected: they're heavier when idle (REQ-080) and don't look native.

## ADR-002: The shell extension is native C++, not managed — *accepted*

**Context:** Infotip handlers run *inside explorer.exe*. Microsoft explicitly recommends against
writing in-process shell extensions in managed code, because of runtime version conflicts, load
time and stability risk.
**Decision:** A small C++20 DLL with a static CRT and SQLite compiled in, read-only.
**Consequences:** Two languages in the repo. Path normalization exists twice, so we keep shared
test vectors (`06-testing.md`) to make sure both implementations agree.

## ADR-003: Central SQLite DB as the source of truth, sidecars opt-in — *accepted*

**Context:** Notes have to be searchable, survive renames, and not pollute user folders (principle 2).
**Decision:** One SQLite DB per user, in WAL mode, with the app as the single writer. Sidecar
`.foldernote.json` files are written only per note and only when the user opts in.
**Consequences:** Notes don't travel with folders by default (mitigated by export and the opt-in
sidecar). The shell extension can read the DB directly, so there's no IPC and no dependency on the
app running.

## ADR-004: Explorer tracking via IShellWindows + WinEvents — *accepted (S1, 2026-10-31)*

S1 confirmed it. `EVENT_OBJECT_NAMECHANGE` + `EVENT_SYSTEM_FOREGROUND` + minimize events catch
every scenario (navigation, same-name folders, tabs, window switch) within the 150 ms budget. The
active tab is found as the visible `ShellTabWindowClass`. `DWebBrowserEvents2` sinks are **not
needed**. Details are in `04-explorer-integration.md` § S1 findings.


**Context:** We need the active folder of the foreground Explorer window, including Windows 11 tabs.
**Decision:** `IShellWindows` enumeration plus `DWebBrowserEvents2`, with foreground and location
WinEvent hooks and a 250 ms poll fallback while Explorer has the foreground.
**Alternatives:** UI Automation reading the address bar (fragile, localized); a shell extension
that pushes events from inside Explorer (more in-process risk).
**Open question:** how reliable active-tab detection is on Windows 11. S1 decides.

## ADR-005: Two-tier context menu — *accepted*

**Context:** The Windows 11 top-level context menu only accepts `IExplorerCommand` handlers from
packaged apps (sparse package allowed). Classic registry verbs only appear under "Show more options".
**Decision:** Ship the Tier 1 registry verb for the MVP (no DLL, no package). Add Tier 2
`IExplorerCommand` with a sparse package in Phase 4b.
**Consequences:** Windows 11 users get one extra click in the MVP.

## ADR-006: Tooltip mechanism — *accepted (S3, 2026-10-31)*

S3 confirmed it. A per-user `IQueryInfo` handler for `Directory` is called by Explorer on
Windows 11 in Details, List and the icon views, and its text replaces the default tooltip. The
`desktop.ini` fallback isn't needed for v1. Still open: E_FAIL fallback behaviour and tooltip
caching (verified in T4.3), plus nav pane, Desktop and Tiles/Content (manual check in T4.5).


**Decision (provisional):** An `IQueryInfo` infotip handler registered for `Directory` in HKCU.
**Fallback if S3 fails:** an opt-in `desktop.ini` `InfoTip` mirror (REQ-073), plus an expanded
panel preview to make up for it.

## ADR-007: Typed COM interop only, no `dynamic` — *accepted (S1, 2026-10-31)*

**Context:** In S1 the C# `dynamic` COM binder crashed with `ArgumentException` in
`ComTypeLibDesc.GetFromTypeLib` when two STA threads late-bound to Shell objects at the same time.
Late binding was also slow (34 ms average per evaluation).
**Decision:** All COM goes through typed interfaces generated by CsWin32 or declared with
`[GeneratedComInterface]`. Late binding (`dynamic`, `InvokeMember`) is banned outside `spikes/`.

## ADR-008: The companion panel is a WinUI 3 window owned by Explorer — *accepted (S2, 2026-10-31)*

**Context:** S2 needed to show that a WinUI 3 window can dock to Explorer without stealing focus,
lagging or leaving gaps.
**Decision:** Use a WinUI 3 `Window` with `GWLP_HWNDPARENT` = the Explorer frame,
`WS_EX_TOOLWINDOW | WS_EX_NOACTIVATE`, `Show(false)`, a PerMonitorV2 manifest, and repositioning
from PID-filtered WinEvent hooks. XAML Islands / a Win32 host isn't needed.
**Consequences:** One UI stack for the whole app. The app has to manage re-owning and detaching
on destroy itself.

## ADR-009: Folder lookup is ID-first, with "recreated at the same path" re-binding — *accepted (S4, 2026-10-31); amended by ADR-020 (same volume only)*

**Context:** S4 showed that delete + recreate gives a new file ID, which would detach notes from
rebuilt folders like `bin\`. A path-first lookup, on the other hand, would wrongly attach a note
to a new folder created where a moved folder used to be.
**Decision:** Look up by file ID first. On a path match with a different ID, attach (and re-bind)
only if the original ID no longer resolves. Canonicalize paths with `GetFinalPathNameByHandle`.
See `03-data-model.md`.

## ADR-010: The FTS5 index stores its own text, keyed by `notes.rowid` — *accepted (T1.5, 2026-10-31)*

**Context:** Spec 03 first had a contentless FTS5 table (`content=''`). Contentless tables can't
`UPDATE`, and deleting a row needs the old column values. They also can't return the text for
`highlight()` or `snippet()`, which the search palette needs (05 § Search palette). An external
content table would need triggers across `notes` and the label junction table.
**Decision:** A normal FTS5 table that stores its own copy of title, body, labels and path. The
repository writes it, with `rowid = notes.rowid`. `notes` rows are never replaced
(`INSERT OR REPLACE`), so the rowid stays stable. `VACUUM` must be followed by an index rebuild.
**Consequences:** The note text is stored twice (about 2× the body size, which is fine at 10k
notes). Deletes and updates are single-row operations by rowid. Highlights come straight from FTS5.

## ADR-011: Single writer = one connection + one Channel-drained task — *accepted (T1.5, 2026-10-31)*

**Context:** SQLite allows one writer at a time. Several app components (editor autosave, panel,
orphan scan, import) write concurrently.
**Decision:** `SqliteNoteStore` owns one write connection. Every write is a delegate posted to an
unbounded `Channel` and run in its own transaction by a single background task. The caller awaits
a `TaskCompletionSource`. Reads open pooled `Mode=ReadOnly` connections and rely on WAL snapshots.
`NoteChanged` is raised after commit.
**Consequences:** There's no `SQLITE_BUSY` between our own writers, and writes are applied in
order. Event handlers run on the writer task, so UI subscribers must marshal to their dispatcher,
and a slow handler delays the next write.

## ADR-012: Tray icon via `Shell_NotifyIcon` on our own hidden window — *accepted (T2.1, 2026-10-31)*

**Context:** WinUI 3 has no tray icon API. REQ-080 makes the app a tray process that must stay
under 60 MB idle, and it has to survive Explorer restarts.
**Options:** a third-party package (H.NotifyIcon, WinUIEx); WinForms `NotifyIcon`; our own
`Shell_NotifyIcon` call via `LibraryImport`.
**Decision:** our own small `TrayIcon` class: a hidden **top-level** window (not message-only,
because message-only windows don't receive the broadcast `TaskbarCreated` message) created on the
UI thread, whose window proc handles the callback message, shows a `TrackPopupMenu` menu and
re-adds the icon on `TaskbarCreated`. P/Invoke is source-generated (`LibraryImport`), typed, and
uses no `dynamic` (ADR-007).
**Consequences:** About 300 lines we own, no extra dependency, and no WinForms runtime loaded
(which would cost memory). The menu is a classic Win32 menu, not Fluent; that matches what the
Windows shell does for tray menus and is acceptable for v1.

## ADR-013: Design tokens in XAML theme dictionaries; status icons as Fluent path geometry — *accepted (T2.2, 2026-10-31)*

**Context:** REQ-082/083 need light, dark and high-contrast support with AA contrast for 12 label
colours, and status icons that look the same on Windows 10 and 11.
**Options:** colours in C# (computed per theme at run time) vs. XAML `ThemeDictionaries`; icons
from the Segoe Fluent Icons font (Windows 11 only, Windows 10 has the older MDL2 font with no
archive glyph) vs. the Fluent System Icons SVG geometry in `PathIcon`s.
**Decision:** one `Themes/Tokens.xaml` with `Light`/`Dark`/`HighContrast` theme dictionaries is
the only place colours exist (05 § Design tokens). The values are precomputed (derivation in 05)
and a unit test parses the file to re-check the contrast rules, so the file can be edited by hand
without silently breaking AA. Status icons are the 20 px regular Fluent System Icons paths (MIT,
`@fluentui/svg-icons` 1.1.292), stored as string resources and rendered with `PathIcon`.
**Consequences:** `{ThemeResource}` switches colours live with no code. Code that needs a token
for a run-time key (a label's colour) goes through `ThemeTokens`, which reads the dictionary for
the element's `ActualTheme`. Adding a status or palette colour means editing `Tokens.xaml`, and
the tests fail until every theme has it. A hex-colour lint test keeps colours out of other files.

## ADR-014: Editor = one view model per session; drafts are saved on first edit — *accepted (T2.3, 2026-10-31)*

**Context:** REQ-003/005/006 need a pre-filled editor, autosave without a Save button, and delete
with undo. Opening "Add folder note…" by accident shouldn't leave empty notes behind. The logic
has to be testable without a XAML runtime.
**Decision:** `NoteEditorViewModel` (CommunityToolkit.Mvvm) holds the whole session. Timers go
through `TimeProvider` and callbacks through `IUiDispatcher`. A new note is a draft until the
first edit or an explicit `Ctrl+Enter`. On close, invalid fields go back to their last saved
value and everything else is saved, instead of blocking the close or dropping every change.
Markdown is parsed by Markdig into an app-owned model and rendered by our own small
`RichTextBlock` renderer, not by a third-party WinUI Markdown control (none ships for Windows App
SDK 2.x that we'd trust, and the panel needs the same output).
**Consequences:** No orphan empty notes; nothing valid is lost on close. The view stays thin, and
every rule in 05 § Editor behaviour is unit-tested with a fake clock. We own the renderer, but its
scope is limited to the REQ-007 subset. Concurrent edits are last-write-wins for now.

## ADR-015: Reuse one hidden editor window instead of destroying it — *accepted (T2.3, 2026-10-31)*

**Context:** REQ-080 keeps the tray process small, so T2.1 destroys windows on close. Measured in
T2.3 (Release): every open/close of a destroyed editor window left about 4 MB of native memory
behind (private bytes 83 → 108 MB over 8 cycles). Without UI Automation attached the result was
the same, a forced GC didn't help (the managed heap is about 1 MB), and the plain main window
showed the same pattern at a smaller scale. The memory is held natively by WinUI, not by our objects.
**Options:** keep destroying windows (unbounded growth); host editors in a child process (large
change); hide one window and reuse it.
**Decision:** `EditorWindow` hides on close, and `AppShell` keeps one hidden window and attaches the
next `NoteEditorViewModel` to it (02 § Editor). Only extra concurrent editors are destroyed.
**Consequences:** Memory is flat over repeated use (≈65 MB private working set / ≈83 MB private
bytes after 8 cycles, ±2 MB). The first editor's one-time cost (≈33 MB over tray-only) stays for
the process lifetime, which is the REQ-080 gap recorded as O-15 (resolved by ADR-016).
*Extended in T2.4:* the main window is hidden and reused the same way (02 § App shell). A reused window must reset
per-session UI state (`NoteEditorView.ResetForNewSession`). The main window (T2.4) should get the
same treatment once it holds the library.

## ADR-016: Memory budgets per app state; no working-set trimming, no separate UI process — *accepted (2026-11-01)*

**Context:** REQ-080 said "under 60 MB idle", measured both tray-only and after a window was used.
After T2.3 the tray-only state is ≈32 MB, but once any WinUI window has been used the process sits
at ≈65 MB private working set (≈83 MB private bytes) for its lifetime: the one-time cost of
loading WinUI's controls (ADR-015, O-15). Folder Notes is meant to run all day next to Explorer,
and from Phase 3 the companion panel keeps a window loaded whenever Explorer is in use, so
"tray-only with every window closed" will be the uncommon state.
**Options:** (1) trim the working set when idle: Task Manager shows ≈3 MB, but commit stays at
83 MB, reopening takes page faults, and it only improves the reading; (2) set budgets per app
state; (3) host windows in a child process that exits on close: frees the memory, but adds
≈0.5–0.9 s to every open, needs IPC, breaks the single writer (ADR-011), and stops helping once
the panel is always loaded.
**Decision:** Option 2, chosen by the user. REQ-080 now has a budget per state, in private working
set: tray-only < 50 MB, editor open or windows used < 90 MB, panel active < 110 MB. These are
initial engineering targets and get re-baselined after Phase 3 (O-16). Alongside them, NFR-06
covers what matters for an all-day companion: idle CPU, no growth across open/close cycles and
extended sessions, and Explorer staying responsive. `eng/perf-check.ps1` measures all of it and is
run as a regression check (06 § Resource budgets).
**Not allowed:** working-set trimming (`EmptyWorkingSet`, `SetProcessWorkingSetSize`) and a
separate UI process. The app stays one process with one database writer (ADR-011). `IdleTrim`'s
compacting GC stays, because it releases real managed memory.
*Amended 2026-11-01 (T2.6, the user's decision):* "windows used" goes from **< 90 MB to < 100 MB**.
With the editor, the main window and the search palette all used, the process measured 91–93 MB,
flat over 8 open/close cycles of each (no leak): the palette window costs about 10 MB once. Two
cheap fixes changed nothing measurable (creating the Labels and Settings pages on first visit,
kept; and a solid background instead of Acrylic on the palette, reverted). A lighter results list
isn't pursued without profiling evidence that it would save meaningfully. Tray-only (< 50 MB) and
panel (< 110 MB) are unchanged, and the post-Phase-3 re-baseline (O-16) still applies. Guidance
from the user: prefer stable, predictable resource use over chasing small, flat increases; what
must never happen is growth.
**Consequences:** Budgets are honest (what Task Manager shows is what the app uses) and need no
runtime code. A looser target can creep, so the check also fails on growth (≤ 4 MB over 8 cycles,
≤ 8 MB over the 120-cycle soak) and is run before ticking any task that adds a window. First run
(Release, 2026-11-01): tray-only 32.2 MB; editor open ≤ 66.6 MB; after close ≤ 67.1 MB; growth
0.4 MB; idle CPU 0 % tray-only and 0.05 % after use. All pass.

## ADR-017: The library updates edited rows in place and reloads only for structural changes — *accepted (T2.4, 2026-11-01)*

**Context:** The detail pane autosaves every 500 ms while the user types (REQ-005), and each save
raises `NoteChanged`. Reloading the whole list on every save means up to 10k rows read per save
(NFR-05), and with the default *Last updated* sort the row being edited would jump to the top and
lose its place under the user's pointer. Keeping the list exactly sorted and filtered after every
change would need the SQL ordering and filters duplicated in C#.
**Decision:** `Updated` re-reads only that note and replaces the row's content in place; the row
keeps its position and stays even if it no longer matches the filters. `Deleted` / `Purged` remove
the row. `Created`, `Restored`, `Relinked`, `OrphanStateChanged` and `LabelsChanged` reload the
list through `ListAsync`, coalesced so at most one reload runs and at most one more is queued.
Changing the sort or filters, or reopening the window, also reloads.
**Consequences:** Typing in the detail pane costs one `GetByIdAsync` per save, and the row stays
put. The order can be stale after edits (an edited note isn't moved to the top) until the next
reload, which is the expected behaviour in list+detail apps. The ordering and filter logic stays
in one place (`NoteFilterSql`).

## ADR-018: Label deletes ask first instead of offering undo; open editors follow label changes — *accepted (T2.5, 2026-11-01)*

**Context:** Deleting a label removes it from every note (03). Notes get a 10 s undo (REQ-006),
but undoing a label delete would need the store to remember which notes had it. Separately, an
editor that stays open (the library's detail pane survives switching to the Labels page) holds
`Label` objects from when it loaded: after a rename it would show the old name, and after a
delete its next autosave would re-create the label by name (unknown names create labels, 03).
**Decision:** A label delete asks for confirmation, saying how many notes lose it, and has no
undo. Every open editor refreshes its labels on `LabelsChanged`: current names and colours
replace the old ones, and labels that no longer exist are dropped without counting as an edit.
**Consequences:** No new store API for undo. Deleting is a deliberate two-step action. An editor
never resurrects a deleted label, and chips in open editors always match the Labels page. If the
user had unsaved label edits in an editor at that moment, only the deleted label is lost from
them (it no longer exists).

## ADR-019: The palette is a reused popup window; the hotkey lives on the tray window — *accepted (T2.6, 2026-11-01)*

**Context:** REQ-050 needs a hotkey that works from any app, and the palette must appear quickly
and in front of the app the user is in. WinUI has no global hotkey API. A new window per opening
would leak native memory (ADR-015) and pay the creation cost each time.
**Decision:** `RegisterHotKey` on the tray icon's hidden Win32 window (it already exists, ADR-012,
and lives on the UI thread). The palette is one WinUI window without a title bar, hidden from the
taskbar and Alt+Tab, created on first use and hidden after that. It closes on `Esc`, on losing
focus and after an open action, the usual command-palette behaviour. Ctrl+C copies the selected
note's path only when the box has no selected text, so normal text copy still works.
*Added during T2.6 (found live):* `Activate()` alone left the palette behind the app the user was
in (the foreground lock), so typing went to that app. The palette now briefly attaches to the
foreground window's input thread (`AttachThreadInput`), calls `BringWindowToTop` +
`SetForegroundWindow`, and detaches; and it puts the caret in the box when the window is actually
activated, because focus set before that is lost.
**Consequences:** The first opening pays for creating the window (measured in T2.6), later ones
don't. The hotkey works while the app runs, including tray-only. If another app owns the hotkey,
registration fails and only the tray can open the palette until Settings (T2.8) lets the user
pick another one. The palette's window adds to the "windows used" memory (REQ-080).

## ADR-020: Orphan handling never guesses: same volume only, conditional writes, conflicts orphan — *accepted (T2.7, 2026-11-01); amends ADR-009*

**Context:** T2.7 makes orphan detection and relinking user-facing. The user asked for data
integrity first: an occasional orphaned note is acceptable, a note attached to the wrong folder or
a lost note is not. Reviewing the T1.5 code against that found four ways to get it wrong:
(1) ADR-009's "recreated at the same path" rule didn't check the volume, so a *different* drive
mounted at the same letter with the same folder path took the note and overwrote its file ID;
(2) `UpsertAsync` wrote the folder binding and `orphaned_at` from the caller's copy, so an editor
open during a relink put the old folder back on its next autosave; (3) a scan decision was based
on a read and applied later, so it could overwrite a relink made in between; (4) a re-bind blocked
by another note left the note silently pointing at a stale path, neither attached nor orphaned.
**Decision:**
- Automatic re-attachment only to the same folder (file ID) or to a folder recreated at the same
  path **on the same volume serial**. `Locate` now tells `VolumeNotMounted` apart from `NotFound`,
  so an unplugged drive shows as "drive not connected" and recovers when it's back.
- `RelinkAsync` and `SetOrphanedAsync` take the binding the caller saw (`expectedFolder`) and
  refuse (`NoteBindingChangedException`) if it changed; the scan, the lookup's re-bind and the
  Orphaned page all pass it.
- Upsert keeps an existing note's binding and orphan state; only relink/orphan operations change
  them. Import (an explicit restore, T1.7) keeps its documented behaviour of taking the imported
  binding.
- A re-bind that conflicts with another live note changes neither note; the moving note is
  orphaned with the reason. Nothing is merged or taken over automatically.
- User relinks are explicit (folder picker), refuse folders that have a note, files and Recycle
  Bin folders, ask when the folder name differs, and offer Undo for 10 s. Nothing in this flow
  changes the note's content, labels, dates or `updated_at`.
**Consequences:** Some situations that could have been auto-repaired now need one *Relink…*: a
drive restored from a backup or reformatted (new serial), a cross-volume move, or two notes
fighting over one folder. The scan reads full notes (`ListAsync`) to classify them; fine at the
current scale, and a light binding-only query is the fix if T5.5's 10k-note measurement shows a
cost. Undo of a relink sets `orphaned_at` to the undo time rather than restoring the old timestamp.

## ADR-021: Main-window pages are created in code on first visit, not with `x:Load` — *accepted (T2.7, 2026-11-01)*

**Context:** T2.6 deferred the Labels and Settings pages with `x:Load="False"` and realized them
with `FindName` to save memory (REQ-080). In T2.7's live check, opening any deferred page crashed
the app: `FindName` returned null, at HEAD too, so the bug shipped in T2.6 (its live check never
opened those pages). The reason: the XAML compiler realizes deferred elements through the owner's
`FindName`, and a WinUI 3 `Window` isn't a `FrameworkElement` (binding `x:Load` with `x:Bind`
doesn't compile there for the same reason). So `x:Load` can't work for elements declared directly
in a `Window`.
**Decision:** `MainWindow.xaml` has an empty `PageHost` grid; `EnsurePage` creates the Labels,
Orphaned and Settings pages (`UserControl`s; the Settings stub became `SettingsStubPage`) and adds
them to it on first visit. Pages stay alive while the window does, as before.
**Consequences:** Same memory profile as T2.6 intended (a page costs nothing until opened). Future
pages follow this pattern; `x:Load` stays usable inside `UserControl`s and data templates
(the Labels page's rename box uses it). The live check of every task that adds a page opens it.

## ADR-022: Settings live in the database; "start with Windows" is the Run entry, defaulted by the installer — *accepted (T2.8, 2026-11-01)*

**Context:** REQ-081 needs persistent settings; 03 already has a `settings` table. REQ-080 says the
app starts with Windows "default on". An unpackaged app that registers itself on first run would
also register every development and `perf-check` build folder on this machine, and a Run entry the
user never chose is the kind of quiet machine change the principles avoid. A global hotkey can be
taken by another app at any time.
**Decision:** Settings are key/value strings in the `settings` table, written through the single
writer; the app parses them with defaults (bad values never stop startup). *Start with Windows* has
no stored value: the Run entry (`HKCU\…\Run\FolderNotes`) is the truth, the toggle reads and writes
it, and the app never creates it on its own. The installer (T6.1) enables it by default, which is
where "default on" is met; a packaged build uses `StartupTask`. If the entry exists but points at
another exe path, the app rewrites it to its own path (the user already opted in). Changing the
hotkey registers the new one first and only then saves; if it's refused, the previous one is
registered again.
**Consequences:** Settings are included in database backups and migrations. Before T6.1, a fresh
install from source starts with Windows only after the user turns it on. The settings page shows
the real registration state, including entries the user removed elsewhere (Task Manager's Startup
tab).

## ADR-023: Import is preview-then-apply with a snapshot; the export format stays v1 — *accepted (2026-11-01, user decision O-21)*

**Context:** Folder Notes will hold valuable information, so backup and recovery matter. The Core import
(T1.7) resolves every conflict with one global policy, replaces notes, label colours and folder bindings
without showing the user, and has no undo. A format v2 (content hashes, app version, checksum) was considered.
**Decision:** Import becomes two steps: a strictly read-only preview, then an apply with a resolution chosen
per conflict (keep mine / take imported / keep both) and per differing label colour, after an automatic
verified snapshot and inside one transaction. Binding changes are flagged in the preview. The file format stays
`foldernotes-export/1`, with byte-identical re-export and v1 reading kept. Content hashes, app version metadata
and checksums are not added now; revisit if a requirement needs them. The snapshot is restored by hand (steps
in 03), not by the app.
**Consequences:** More Core surface (`ImportPlan`, resolutions, `ISnapshotService`), a Settings UI, and tests
for the read-only guarantee and rollback. The policy-based `ImportAsync` stays as a wrapper. Scheduled in
Phase 5 after the daily backup (T5.3), which shares the snapshot mechanism.

## ADR-024: Explorer verbs are registered by the installer; the app only offers a manual toggle — *accepted (T3.1, 2026-11-01, user decision)*

**Context:** The Tier-1 verbs (04 § 4.1) are `HKCU\Software\Classes\Directory\...` keys whose command holds
the exe path. The task said "on first run". Registering from the app on first launch would also register every
development, test and `perf-check` build, and leave stale commands in the user's Explorer menu. This extends ADR-022.
**Decision:** No code path registers the verbs automatically: not on first launch, and not through any switch
used by tests or `perf-check`. The installer (T6.1) registers them on install and removes them on uninstall
(through `FolderNotes.exe --unregister-shell` or its own steps). The user can turn them on or off in Settings
(*Folder note in the right-click menu*). `ShellVerbRegistrar` reports the **actual** state from the registry:
*Off* (no keys), *On* (both keys, commands match this exe), *Stale* (a key exists whose command points to another
or a missing exe, or only one of the two keys exists). Settings shows Stale as "Incomplete, or registered for a different
copy of Folder Notes (<path>)" with **Repair** (rewrite for this exe) and the toggle off to remove. A failed write is reported
and the state re-read, never assumed. The app never repairs on its own and only touches the `FolderNotes` key
under the two `shell` parents.
**Consequences:** A fresh install from source has no menu entry until the user turns it on; the installer meets
the original "registered on first run" intent. Tests use a scratch registry root, never the real keys.
